# Wire protocol, v1

Both implementations (`android/`, `macos/`) MUST match this document byte for
byte. `docs/test-vectors.json` is generated by an independent Python
implementation (`scripts/gen_test_vectors.py`) and both sides test against it.

Notation: `||` is concatenation. `b64url` is base64url **without padding**.
ASCII string literals are UTF-8 bytes with no terminator.

## Identities and keys

Each device has, generated once and stored locally:

| Device | Id                    | Key pair       |
|--------|-----------------------|----------------|
| Mac    | `macId`: 16 random bytes   | X25519 `macPriv` / `macPub` (32 B)   |
| Phone  | `phoneId`: 16 random bytes | X25519 `phonePriv` / `phonePub` (32 B) |

The session key for a (Mac, phone) pair is static:

```
shared = X25519(myPriv, peerPub)                      # 32 bytes
K      = HKDF-SHA256(ikm  = shared,
                     salt = "wifi-bridge/v1",
                     info = macPub || phonePub,       # always Mac first
                     L    = 32)
```

### Sealing

```
seal(K, aad, pt)  = nonce(12 random) || ChaCha20-Poly1305(K, nonce, aad, pt) || tag(16)
open(K, aad, box) = inverse; any failure is an authentication error
```

This is the CryptoKit `ChaChaPoly.SealedBox.combined` layout, and the layout of
Tink's `subtle.ChaCha20Poly1305`.

## Pairing QR (shown by the Mac)

The QR encodes a URI, so the phone's normal camera app hands it to wifi-bridge:

```
wifibridge://pair?p=<payload>
payload = WBPAIR1;<b64url macId>;<b64url macPub>;<b64url pairSecret>;<b64url utf8 macName>
```

The phone accepts the URI (with `p` raw or percent-encoded) and, for
compatibility with v0.1/v0.2 Macs, the bare payload. Opening the link shows a
confirmation ("Pair with *macName*?") before anything is stored — any web page
can fire a `wifibridge://` link.

`pairSecret` is 16 fresh random bytes per pairing attempt, valid 10 minutes.
The QR is the trusted channel: it gives the phone `macPub`, and gives the Mac a
secret only a phone that scanned it can know.

## GATT layout (phone is the peripheral)

| Item            | UUID                                   | Properties          |
|-----------------|----------------------------------------|---------------------|
| Service         | `c86d1f45-41c6-43d2-a031-789f6b73e9d1` | primary, advertised |
| INFO            | `1d4fe1b5-e225-4a93-9a96-7997402eec3d` | read                |
| RX (Mac→phone)  | `222462df-2917-4ddb-97ac-5459a7f90a44` | write (with response) |
| TX (phone→Mac)  | `cc6d3b26-2fe0-4ed4-a3e2-fba6032b3ad6` | notify              |

The advertisement carries the 128-bit service UUID only (no device name), so it
fits in a legacy 31-byte advertisement.

INFO value (49 bytes): `0x01 (protocol version) || phoneId(16) || phonePub(32)`.

## Framing

Messages can exceed one GATT value, so every RX write and TX notification is a
**frame**:

```
frame = header(1) || chunk
header bit 0 (0x01) = FIRST   — receiver discards any partial buffer, starts a new one
header bit 1 (0x02) = LAST    — receiver dispatches the buffer as one message
```

A single-frame message has header `0x03`. Chunk size is
`(negotiated max value length) - 1`, at least 19 (default ATT MTU 23 − 3 − 1).
Receivers drop a message larger than 65 536 bytes and reset. Frames are sent one
at a time: the Mac waits for each write response; the phone waits for
`onNotificationSent` before the next notification.

## Messages

First byte of a message is its type.

| Type | Name           | Dir       | Body |
|------|----------------|-----------|------|
| 0x01 | PAIR_REQUEST   | Mac→phone | `macId(16)` |
| 0x02 | PAIR_ACCEPT    | phone→Mac | `proof(32)` |
| 0x03 | PAIR_CONFIRM   | Mac→phone | `macId(16) || seal(K, "wb-pair-confirm" || macId || phoneId, utf8 macName)` |
| 0x04 | PAIR_DONE      | phone→Mac | empty |
| 0x10 | SYNC_REQUEST   | Mac→phone | `macId(16) || seal(K, "wb-req" || macId || phoneId, json)` |
| 0x11 | SYNC_RESPONSE  | phone→Mac | `seal(K, "wb-resp" || macId || phoneId, json)` |
| 0x7F | ERROR          | phone→Mac | `code(1)` |

```
proof = HMAC-SHA256(key = pairSecret,
                    msg = "wb-pair-phone" || macId || phoneId || phonePub)
```

### Pairing sequence

1. Phone scans the QR → stores a *pending* pairing `{macId, macPub, pairSecret, macName}`
   for 10 minutes.
2. Mac (in pairing mode) scans for the service, connects, reads INFO →
   `phoneId`, `phonePub`. Subscribes to TX.
3. Mac → `PAIR_REQUEST(macId)`.
4. Phone: if a pending pairing for `macId` exists → `PAIR_ACCEPT(proof)`;
   else `ERROR 3`.
5. Mac recomputes `proof` with its `pairSecret` and the INFO values; constant-time
   compare. On mismatch it disconnects and keeps scanning (another phone may be
   advertising). On match it stores the phone `{phoneId, phonePub}` and derives `K`.
6. Mac → `PAIR_CONFIRM`. Phone opens it with `K` (proves the Mac holds
   `macPriv`), stores the Mac as paired, clears the pending entry → `PAIR_DONE`.

### Sync

Request JSON:

```json
{ "n": "<b64url 16 random bytes>", "ssids": ["Casita_Guest", "Other"], "all": false }
```

- `all: true` asks for every network in the vault (manual "sync everything");
  `ssids` is then ignored.
- Otherwise the phone returns the vault networks whose SSID is in `ssids`
  (exact, case-sensitive), plus none of the rest.

Response JSON:

```json
{ "n": "<same as request>", "status": "ok",
  "networks": [ { "ssid": "Casita_Guest", "security": "WPA", "password": "…", "hidden": false } ] }
```

`status` is `ok`, `denied` (user tapped Deny), or `timeout` (approval prompt
expired after 60 s). `networks` is empty unless `ok`. `security` is one of
`WPA`, `WEP`, `SAE`, `nopass`. The Mac MUST reject a response whose `n` differs
from the request it sent.

### Approval

Each paired Mac has a phone-side setting **Share automatically** (default on).
When off, a SYNC_REQUEST posts a notification with *Share* / *Deny* actions; the
phone answers when tapped or after 60 s (`timeout`).

### Error codes

| Code | Meaning |
|------|---------|
| 1    | unknown `macId` (not paired) |
| 2    | authentication failure opening a sealed box |
| 3    | no pending pairing for this `macId` |
| 4    | malformed message |

## Threat notes

- The INFO value exposes a stable `phoneId` to anyone in BLE range. Accepted for
  v1; rotate later if it matters.
- A replayed SYNC_REQUEST yields a response only the paired Mac can open.
- A response replayed to the Mac fails the `n` check.
